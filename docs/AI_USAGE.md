## 1. 使用原则

本项目在部分阶段使用 AI 编程助手辅助代码阅读、测试起草、命令准备、附件解析、数据汇总和文档整理。AI 输出不作为实验成功的依据；报告中的提交、任务号、退出码、日志、artifact 和 SHA-256 必须来自 Git、CI 或实际运行证据，并由成员审核。

成员不把 AI 代理执行、其他组员操作或 B04 操作改写为本人手工完成。涉及账号、GitHub 授权、服务器权限、方案取舍和最终提交的决定由学生负责。真实密码、令牌和私钥不写入提示、源码、报告或证据包。

## 3. 采纳、修改与拒绝的代表性实例

### 3.1 采纳

- 使用独立输出目录、保留失败证据并为 artifact 记录 SHA-256，增强可审计性。
- 为 E8–E10 增加间接 include、声明变化和深层 include 等独立预期测试，而不是复制参考实现。
- 对 B04 回执逐项核对 job/trace、URI、字节数和 SHA-256，不仅依赖“成功”文字说明。
- 期末证据按成员、阶段和归属分包，并在本机进行外层压缩包及内部文件双层校验。

### 3.2 修改或拒绝

- 拒绝把未执行的服务器实验、validation checks 或 PR 审查写成已完成。
- 拒绝为了更好看的性能数字删除小于 1 的加速比。
- 拒绝在时间受限时把保守缓存策略改为精确失效，以免改变 30 行矩阵语义且缺少回归证明。
- 拒绝把受控构造的 SDS 缺陷称为上游真实历史 bug。
- 拒绝把 `v0.9-rc` 标签存在等同于正式发布通过。

## 4. 验证方法

AI 辅助产生或整理的内容通过以下方式检查：

1. 运行单元测试、合同测试和四服务 E2E；
2. 使用 GitHub Actions 必需检查和受保护分支；
3. 对比增量与全量 findings；
4. 检查补丁应用、构建、程序输出、头文件变化和终检结果；
5. 核对任务 `job_id`、`trace_id`、base/target commit；
6. 重算 artifact、补丁、回执包及最终证据包 SHA-256；
7. 保留失败→修复→成功的成对证据；
8. 由成员确认贡献归属和未覆盖风险。
