三点必须解释清楚的现象：

1. C1 的 `C1-build.log` 只有 `gcc -O0 -c main.c -o main.o` 和 `gcc main.o helper.o -o app`，helper.o 没有重编；但依赖扫描两个目标都复用。说明「依赖分析复用」不等于「make 不会执行任何编译」。
2. C2 里 `make app` 退出码为 0、程序仍可构建，但 `actual.main.o` 已经多出 extra.h 而声明没有，于是新增一条 MD。构建成功不能证明依赖正确。

## 新增用例/输入/独立预期及验证结果

先写预期，再跑代码（预期不是从实现里抄出来的）：

```python
    def test_nested_include_invalidates_whole_graph(self):
        # 间接头文件：main.c -> config.h -> nested.h；直接文件 main.c 未改，旧图仍必须失效
        old=scan(self.p)
        (self.p/'nested.h').write_text('#define NESTED 1\n')
        (self.p/'config.h').write_text('#include "nested.h"\n'+(self.p/'config.h').read_text());commit(self.p,'nested include')
        r=scan(self.p,old)
        self.assertEqual(r['actual']['main.o'],['config.h','main.c','nested.h'])
        self.assertEqual(r['refreshed'],['main.o','helper.o'])
        self.assertEqual(r['reused'],[])
        self.assertIn(['MISSING','main.o','nested.h'],r['added'])
        self.assertEqual(len(r['findings']),3)
```

独立预期与实测：

- 预期 `actual.main.o` 含 `nested.h`（`gcc -MM` 会带出间接头）→ 实际 `['config.h','main.c','nested.h']`
- 预期 `key.directives` 因 config.h 变化而不同，保守刷新**两个目标**（helper.o 的源文件没动也一起刷）→ 实际 `refreshed=['main.o','helper.o']`、`reused=[]`
- 预期新增一条 MD `nested.h`、findings 从 2 条变 3 条 → 实际 `added=[['MISSING','main.o','nested.h']]`、3 条

## 论文机制对应、教学简化与扩展计划

- 对应点：EChecker 的核心主张是「用历史依赖图 + 保守失效判据做增量检查，并用全量结果做等价性对照」。本实验把这条主张落成 `key = {directives, recipes, flags, compiler}` 的可比较结构：任一维变化即整图刷新，等价于论文里的保守超集失效。
- 教学简化：只用两个对象目标（main.o/helper.o）与 C 语言本地头，不做链接期、宏配置矩阵和目标粒度剪枝；`gcc -MM` 代替真实编译器的依赖回调，因此「依赖」定义为预处理可见的头文件集合。
- 扩展计划：①把全目标刷新改为「受影响目标 + 传递闭包」，用本实验的 30 行矩阵做回归对照，确认没有漏边；②增加文件删除与 `-DMODE=1` 配置切换两个场景；③把计时从单次 `scan()` 扩展到包含增量编译的端到端口径。
